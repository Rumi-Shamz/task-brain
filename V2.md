# task-brain — v2 agent brief

Work through tasks **in order**. One task = one branch + one PR. Do not start task N+1 until task N is merged.

## Context

- App: `rumi-shamz/task-brain`, served by GitHub Pages. Vanilla HTML/CSS/JS, **no build step**, no framework. Keep it that way.
- Tabs: 01 Triage · 02 Organize · 03 Schedule · 04 Year · 05 Dashboard.
- Sync: `data.json` is committed through the GitHub API using a fine-grained PAT stored on the device.
- Weekly loop: a voice planning session follows a script, a CSV is produced, and the CSV is imported into the app.
- Owner's activity model: each project has three activity rows, **Research/Plan · Communicate · Act**. v2 adds a fourth row, **Learn**.

## v2 goal

Close the weekly loop: voice session → transcript → validated JSON → app → next week's review is generated from app data.

**v2 is done when** three consecutive weekly cycles run with zero manual fixes to imported data.

## Hard constraints

1. No secrets in the public repo. No API keys in client-side JS, ever.
2. Personal data lives only in a **private** repo.
3. No new dependencies without asking the owner first.
4. No behavior changes outside the scope of the current task.
5. Every data-shape change ships with a migration for existing `data.json` (bump `version`).

## Tasks

### T0 — Move data to a private repo (security, do first)
- Create the private repo `task-brain-data`. Point the sync settings at it.
- Remove `data.json` from `task-brain` **and from its git history** (`git filter-repo`).
- Acceptance: `https://raw.githubusercontent.com/rumi-shamz/task-brain/main/data.json` returns 404.

### T1 — Split `index.html` into ES modules (no behavior change)
- Target modules: `state.js`, `storage.js`, `sync.js`, `triage.js`, `organize.js`, `schedule.js`, `year.js`, `dashboard.js`, `ui.js`.
- Use `<script type="module">`. Aim for no file over ~400 lines.
- Acceptance: every feature works exactly as before. Do a manual click-through of all 5 tabs plus sync.

### T2 — Data schema + validating import
- Add `schema/plan.schema.json` (JSON Schema) as the single source of truth.
- Domains enum: `ALFA`, `Dorst`, `SwingShuffle`, `SwingSociety`, `SoftwareDev`, `Personal`, `Other`.
- Projects belong to a domain. Example: `Swing Buzz` is a **project** under `SwingSociety`, not a domain.
- Normalize on import:
  - trim strings
  - lowercase `timepressure` (`urgent` | `important`)
  - priority is an integer from 0 to 3
  - `length` is one of 15, 30, 60, or 180
  - a `✕` in the name means `status: "done"`, and the `✕` is stripped from the name
  - rows named `Dump` become `status: "someday"` with `reviewAt` set
- Accept both JSON (preferred) and the legacy CSV.
- Show per-row errors instead of silently importing bad rows.
- Acceptance: the attached `weekly_plan.csv` imports with clear errors or warnings, and no data is lost.

### T3 — Minimal project entity
- Fields: `id`, `name`, `domain`, `objective` (one line), `deadline`, `status`, `people[]`, `links[]`.
- Each task gets a `projectId` and an `activity` field (`research` | `communicate` | `act` | `learn`).
- Out of scope for v2: KPI, OKR, budget, timeline view.

### T4 — LNO tag (replaces the long-term yes/no criterion)
- Field: `lno: "L" | "N" | "O" | null`.
- Migration: `lt: true` becomes `L`, `lt: false` becomes `N`, and `null` stays `null`.
- Triage UI: three pills with hints. L = "10x return, give it your best energy". N = "do it well enough". O = "minimize, batch, delegate first".
- Dashboard: show the % of scheduled minutes spent on L this week.

### T5 — Learn row + skills backlog
- Entity `skill`: `name`, `utility` (high/low), `timeToLearn` (high/low), and `quadrant`, which is derived from the other two:
  - high utility + low time = `now`
  - high utility + high time = `schedule`
  - low utility + low time = `opportunistic`
  - low utility + high time = `decide`
- `schedule` skills generate a recurring weekly Learn block.
- After each learn session, create review tasks at +1, +7, and +30 days (spaced repetition).

### T6 — Someday review + discard rule
- Every `someday` item has a `reviewAt` date. A weekly view lists items that are due.
- The decision flow on each item, in order:
  1. Can someone else do it? → Delegate (Communicate row).
  2. Is there a concrete next action now? → Convert it to a task.
  3. Would anything bad happen if it is never done? If no → Delete.
  4. Otherwise → Push `reviewAt` forward.
- An item skipped at 3 consecutive reviews gets auto-flagged as "delete candidate".

### T7 — Weekly extraction agent (runs outside the browser)
- A script (`scripts/extract_week.*`) takes a transcript and calls the Claude API with structured output against `plan.schema.json`. It writes `week-YYYY-WW.json` to the private data repo.
- Runs either locally or as a manual `workflow_dispatch` GitHub Action. The API key lives in Actions secrets.
- Also produces `prebrief-YYYY-WW.md`, built from last week's data: done vs. planned, hours by domain, % of time on L, someday items due.

## Explicitly out of scope for v2
Inbox/email integration, Drive/Coda/Notion sync, search/map, Jev or other classifier models, multi-user auth, KPI/OKR/budget.
